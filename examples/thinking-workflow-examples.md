# Thinking Workflow：合成场景示例

以下场景全部为虚构组合，不对应任何真实个人、企业、项目或事件。重点是展示五个 Skills 如何分工，而不是提供标准答案。

## 场景一：研究一个陌生主题

### 初始表达

“我想系统理解一个陌生概念，并判断它是否值得用于当前工作。”

### 处理路径

1. `preflight` 先找术语、前例、相邻概念、主要分歧、公开实践和失败方式。
2. `scale` 沿目标、证据、影响和行动向外、向内、横向移动。
3. 当前边界只保留会改变判断的材料；不会改变建议的支线暂时排除。
4. 需要形成方案时用 `fusion`；只需要理解时在此停止。
5. 交付研究结论前用 `postflight` 检查来源、推断和未知是否分开。

## 场景二：几个方案各有优点

### 初始表达

“方案 A 成熟，方案 B 灵活，方案 C 更符合我的审美，能不能融合？”

### 处理路径

- `preflight` 只补齐缺失的公开证据，不无限扩大调研。
- `scale` 明确当前目标、约束和必须一起判断的关系。
- `fusion` 把可借鉴部分降维成原则、结构、流程和取舍。
- 舍弃品牌包装、不可迁移条件、受限资产和功能拼盘。
- 最终输出一个自洽的新方案，而不是来源对照表。

## 场景三：个人自动化准备宣布完成

### 初始表达

“脚本已经跑通，可以结束了。”

### Postflight 检查

- 原始承诺是什么；
- 正常路径和失败路径是否都实际运行过；
- 文件、配置和数据是否可恢复；
- 入口、依赖和使用方式是否可交接；
- 哪些内容仍未验证；
- 下一步是否真的必要。

如果核心路径没有运行证据，就不能把“写完”写成“完成”。

## 场景四：月度人机协作改进

### 初始表达

“我和 Agent 做了很多事，但不知道协作方式是否真的变好了。”

### 处理路径

- 不用会话数、Token、文档数或提交数直接代表价值。
- 选择少量已完成任务，核对真实文件、测试、链接、交付反馈和用户纠正。
- 记录重复成功模式、反复摩擦、影响、反例和置信度。
- 每周期最多提出三个可验证改变。
- 单次现象留作观察；跨任务重复或由使用者明确确认后，才建议进入规则、Skill、脚本或运行手册。

一个合格的实验示例：

> 所有准备宣布完成的自动化任务都使用同一份 Postflight 最小清单，四周后比较遗漏项是否下降。

它有明确动作、观察窗口和验证信号，也允许结论是“无效”。

## 场景五：传统企业内部转型

### 初始表达

“某个跨团队流程重复录入、异常多，希望通过 AI 或自动化一次性解决。”

### 处理路径

1. `preflight` 先检查系统原生能力、成熟产品、连接器、规则配置和“不新增系统”的替代路径。
2. `scale` 沿数据产生、判断、审批、异常和完成证据追踪，不按部门名称机械拆分。
3. `fusion` 把外部实践、现有系统能力和一线操作方式组合成渐进式方案。
4. 执行时先保留人工确认和可恢复路径。
5. `postflight` 验证正常路径、异常路径、权限、日志、回滚、Owner 和交接。
6. `retro-insights` 跨多个周期判断重复异常来自规则、数据、培训还是边界选择。

自动化率不是唯一目标。若自动化把异常成本转移给下游，或让完成状态更难验证，就需要缩小范围或保留人工闸门。
