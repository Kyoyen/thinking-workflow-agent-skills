# Postflight

## 定位

Postflight 是任务末尾的闸门，和 `preflight` 对称。

`preflight` 问：开工前有没有前例、捷径、路由和不该做的事？

`postflight` 问：收工前结果是否可验收、可恢复、可维护、可交接？

不可替代边界：`postflight` 只负责任务完成后的验收、恢复、维护、交接和下一轮；不负责开工前调研、方案融合或设计生产。

参考模型：

- Scrum 的 Definition of Done：完成必须有共享标准，不满足就不能当成完成。
- Google SRE 的 launch checklist：清单要轻、具体、可执行，并持续删旧项。
- Google SRE 的 postmortem：重要事件要留下影响、原因、动作项和复盘沉淀。
- SLO/SLI 思路：长期运行的东西要有可观测指标，而不是只说“应该没问题”。
- PDSA：下一轮不是空泛路线图，而是基于证据的小循环。

## 核心原则

- 先验收，再扩展。不要把收尾变成新项目。
- 证据优先。没跑过、没打开过、没验证过，就明确说未验证。
- 可逆优先。文件、缓存、配置、部署、权限类动作要有回滚或冷藏路径。
- 长久化有选择。只沉淀下次会复用或会踩坑的信息。
- 下一轮只留最小动作。没有必要的优化，不硬造 backlog。

## 触发后先分型

| 类型 | 重点检查 | 常见证据 |
|---|---|---|
| 代码/自动化 | 验收标准、测试、回归、回滚 | diff、测试结果、命令输出、日志 |
| 文档/报告 | 结构、来源、缺口、可交接性 | 文件路径、目录、引用、未确认项 |
| 协作平台 | 链接、权限、负责人、后续任务 | 文档链接、表格/任务状态、权限说明 |
| skill/plugin | 触发词、安装状态、权威仓库、使用路径 | `SKILL.md`、plugin list、smoke test |
| 本机清理/配置 | 只读证据、可逆动作、影响面 | dry-run、扫描报告、备份/冷藏路径 |
| 部署/周期运维 | 监控、告警、回滚、节奏、Owner | URL、health check、runbook、日历/任务 |
| 设计交付 | 设计源、视觉验收、实现一致性 | `DESIGN.md`、截图、对比板、design review |

## 路由

| 如果收尾重点其实是 | 路由或搭配 | 原因 |
|---|---|---|
| 文档、记忆、交接是否过期 | 项目状态与交接对齐 | 对齐当前文档、Agent 记忆和旧指令 |
| 代码正确性或回归风险 | 测试、构建和代码评审 | 需要可执行证据和缺陷风险检查 |
| 实现是不是过度复杂 | 简化审查 | 找可删的抽象、依赖和包装层 |
| 验收标准本身含糊 | 需求拷问 | 拷问目标、边界、假设和接受标准 |
| 设计产物是否过关 | 设计评审 | 处理视觉、交互和实现一致性 |
| 协作平台交付物 | 对应平台的读取与权限核验能力 | 核验链接、权限、负责人和跟进项 |
| skill/plugin 变更 | Skill 校验和安装状态检查 | 确认结构、触发、安装与权威来源 |
| 磁盘清理或本机工具治理 | 只读扫描与 dry-run | 保持可逆、先证据后清理 |
| 部署或周期性运维 | runbook / automation 工具 | 需要监控、回滚、Owner 和节奏 |

## 执行流程

1. 复述承诺：用一句话写清本次任务原本要交付什么。
2. 写验收标准：优先使用用户给的标准；没有就补一个最小公平标准。
3. 对证据：逐项列出已经验证的内容、未验证的内容、无法验证的原因。
4. 判状态：只允许四类：`已验收`、`带 caveat 验收`、`未验收`、`阻塞`。
5. 查运维面：长期运行或会被复用的东西，检查 Owner、入口、回滚、监控/复查节奏。
6. 做长久化：必要时更新文档、记忆、任务、协作链接、runbook、skill 源或交接笔记。
7. 留下一步：只写一个最小后续动作；需要周期化时写清频率和触发条件。

## 验收状态定义

| 状态 | 使用条件 |
|---|---|
| 已验收 | 核心标准满足，关键证据齐全，没有必须处理的风险 |
| 带 caveat 验收 | 可交付，但有明确未验证项、环境限制或低风险后续 |
| 未验收 | 关键标准不满足，继续说完成会误导 |
| 阻塞 | 缺少权限、信息、外部状态或用户决定，当前无法继续验证 |

## 长久化判断

只沉淀这些内容：

- 下次会影响行动的规则、路径、命令、触发词、权限边界。
- 已经验证有效的流程或工具组合。
- 后续必须跟进的 Owner、日期、节奏、风险。
- 用户明确纠正过的术语、偏好或项目事实。

不要沉淀这些内容：

- 一次性流水账。
- 已经被代码或文件名清楚表达的事实。
- 还没验证的猜测。
- 可以用 `git log` 找到的普通历史。

## 输出格式

默认用这个短格式：

```markdown
**Postflight 状态**
已验收 / 带 caveat 验收 / 未验收 / 阻塞。

**验收对照**
- 标准：结果 / 证据。

**未验证与风险**
- 未验证项、剩余风险、回滚或人工确认方式。

**长久化**
- 已记录/已链接/已排期/无需沉淀。

**下一轮**
- 一个最小后续动作；需要时写 Owner、频率、触发条件。
```

如果用户要完整收尾报告，再展开为：

- 背景和目标
- 验收矩阵
- 证据清单
- 风险和回滚
- 运维/周期化
- 文档和记忆变更
- 下一轮动作

## 红线

- 不要声称做过未实际发生的验证。
- 不要为了收尾而新增大范围工作。
- 不要往 `AGENTS.md` 或 `CLAUDE.md` 塞历史流水账；那里只放长期规则。
- 安装、构建、迁移、部署、浏览器/运行时下载、大型网络拉取，都必须走长操作审批门。
- 不要删除文件、缓存或配置，除非用户明确批准。
- 对协作平台执行写操作前，必须确认目标、身份、权限和可回读结果。
- 用绝对日期，不写“今天”“最近”。
