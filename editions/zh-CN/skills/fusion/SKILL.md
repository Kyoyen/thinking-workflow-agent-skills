# Fusion

把多个相似方向的项目和解决方案中的有用理念引入当前问题，消化成一个整体化、一致化、可信化的自有方案。

`fusion` 交付吸收后的完整方案。来源、证据和边界用于工作过程中的判断、去风险和防抄袭；许可证、署名、合规、用户要求或风险说明需要时，保留必要来源说明。

核心动作是五个：取其精华、去其糟粕、排除噪音、服务目标、找到新解法。比较只是手段，融合后的新解法才是结果。

不可替代边界：`fusion` 只负责把已经进入视野的相近方案消化成服务当前目标的新解法；不负责广泛找前例、生产设计规则或做任务收尾验收。

## 硬边界

- 只使用合法可访问的公开材料，或用户明确有权使用的私有材料。
- 可以学习想法、原则、流程、权衡、信息架构、体验模式、组织方式和设计决策。
- 不复制他人的原文、代码、视觉资产、品牌识别、图标、插画、版式细节、数据集、私有实现或商业秘密。
- 不绕过登录、付费墙、权限、robots、许可证、保密约定或平台条款。
- 如果来源有许可证、署名、商用限制或不确定风险，先列出风险，再给出不侵权的替代表达。
- 输出要体现“吸收后的整体方案”，不能把公开成果改名后当成自己的成果。

## 适用场景

- 用户说“把 A 和 B 对比一下，融合成适合我的方案”。
- 用户想把几个相近方向的项目、产品或解决方式中的核心有用理念，引入自己的问题或方案。
- 用户上传或指向两个 GitHub skill 仓库、工具、产品页、竞品页、方案文档或设计参考。
- 用户想“取其精华”，但需要避免抄袭、过拟合或盲目搬运。
- 用户在两个路线之间摇摆，需要保留各自有效部分，形成第三条路。
- 用户要把外部公开实践转成个人工作流、团队规范、skill、PRD、设计 brief、实施计划或验收清单。

## 不适用场景

- 用户明确要求复刻、搬运、规避版权或绕过许可证。
- 关键材料来自泄露文件、私密群聊、未授权账号、未公开报价、内部代码或商业秘密。
- 任务本质是法律意见。只能做风险提示和安全替代方案，不能给法律结论。
- 只需要普通竞品信息，不需要融合方案时，优先使用专门的竞品或调研 skill。

## 开工判断

先问自己四个问题：

1. 这次融合要服务什么目标：效率、质量、审美、增长、运维、成本、学习、决策还是交付？
2. A/B 的证据是否足够：有真实文件、页面、代码、截图、说明、使用反馈或运行结果吗？
3. 哪些东西只能学习思路，不能带走表达、实现或资产？
4. 最终产物需要直接形成整体方案，还是先出内部比较表/融合 brief 再继续推进？

信息不足时，不要编造。先列出缺口，再用本地读取、网页检索、用户补充或小样本试跑补齐。

## 工作流

1. 定义融合问题：明确当前目标、使用者、约束、成功标准和不可做边界。
2. 建立内部证据台账：分别记录来源、可访问状态、许可证/署名信息、更新时间和可信度；这一步用于判断，不等于最终输出要逐条溯源。
3. 统一比较维度：按目标选择 5 到 9 个轴，不要为了对比而对比。
4. 取其精华：把可借鉴部分降维成原则、结构、流程、判断标准或交互模式。
5. 去其糟粕：去掉上下文不适配、维护成本高、过期、风险高或会误导当前目标的部分。
6. 排除噪音：识别表层包装、品牌话术、流行词、装饰性功能、偶然成功因素和不可迁移条件。
7. 服务目标：把留下的理念重新绑定到当前问题、受众、资源、约束和验收标准。
8. 找到新解法：不要拼贴 A+B；用当前目标重新组织，形成整体化、一致化、可信化的路线、结构和验收标准。
9. 做边界复核：确认没有复制代码、文案、视觉资产、私有实现、商业秘密或许可证受限内容。
10. 路由下一步：根据产物类型交给设计、工程、文档、协作平台、竞品分析或 `postflight` 等后续能力。

## 常用比较维度

按任务挑选，不必全用：

- 目标和受众
- 核心机制
- 使用路径
- 信息架构
- 输入和输出
- 成本和维护
- 可扩展性
- 易用性
- 可靠性和风险
- 审美/语气/品牌适配
- 上手成本
- 许可证和使用边界
- 可复用的抽象原则
- 不适合当前场景的部分

## 路由表

| 场景 | 优先路由 |
|---|---|
| 开工前要先找对标、先验证方向 | `preflight` |
| 两个 skill、仓库、工具或工作流要比较融合 | 本 skill，必要时读取真实文件和 README |
| GitHub skill 仓库对比 | 本 skill + 只读仓库评估；不要整包搬运 |
| 产品/竞品公开页比较 | 竞品研究，再回到本 skill 融合 |
| 设计路线、风格或视觉系统融合 | 设计系统与设计评审能力 |
| 方案已经清楚，需要实现 | 对应的工程、运营或变更实施能力 |
| 需求含糊，需要先被盘问 | 需求拷问或业务分析 |
| 融合方案做完，需要验收、长期化、运维化 | `postflight` |

## 输出规则

默认交付要像一个已经消化过的方案，不像比较笔记。不要逐条标注“这个想法来自 A，那个想法来自 B”。除非用户要求、风险较高、许可证需要、或需要证明判断过程，否则把来源、对比表和边界检查保留为内部工作稿，只在必要处简写。

## 质量门槛

- 结论必须回扣当前目标，并给出明确取舍。
- 每个“借鉴点”都保持在原则、结构、流程或判断标准层面。
- 融合方案要有取舍，不做功能拼盘。
- 最终方案呈现自洽结构；来源标签保留在必要的证据记录中。
- 如果证据不足，输出“缺什么证据”，不要假装已经比较过。
- 如果涉及商业、法律、许可证或隐私风险，宁可缩小使用范围，也不要模糊带过。
